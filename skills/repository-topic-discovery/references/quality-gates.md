# 触发、原始意图与贡献边界

仅在这些语义边界难判时读取；常规执行规则已在阶段提示中，不向每阶段重复拼入本文件。

## 触发从哪里来

检查链条：发生什么 → 哪些条件造成困难 → 用户想推进什么 → 原有办法为何不足 → 项目或内容怎样帮助。日常持续需求也成立，无须制造热点。只核实影响判断的时间、地点、平台、成本等条件。

用户给的场景是 `user_context`；公开材料支持的事实是 `source`；补出的假设是 `inference`。三者可共存，但不可互相冒充。一次事件或个人反馈不能代表所有地区与人群；当前赛事、版本等时效事实未经核实要条件化。触发成立本身不证明承接能力。

## 回答程度由原始需求决定

对照原始 need 的受众、目标和帮助类型，候选 query 保留了什么、改变了什么，以及目标入口实际让此人完成什么。主题相近不足以通过，但问题宽泛也不自动失败。

例如“长会话越来越不可靠，1M 上下文有什么用途”可以是已有贡献的发现入口。如果文章确实解释相关现象、比较标称窗口与有效利用，并给出适用边界，它可能满足这个理解/评估需求；无需证明项目能修复所有长会话。仍须核对文章实际内容及对应需求依据，不能只见标题就判满足。

如果原问是“有没有工具让我的长会话不再忘记要求”，仅解释原因的文章通常只能部分帮助，不能把原问改成“为什么会忘”来过关。改变目标或受众得到的是新推导，须重新验证。教程、比较或工具页面都按实际帮助判定，不机械要求问法与页面形式相同。

对贡献题，`capability_supported` 检查内容是否有证据提供所述帮助；不要求产品实现相应功能。对能力题，文章讨论过某功能不能代替产品提供该功能的证据。局部研究结果也不能直接证明实际任务成功或商业效果。

## 缺证据时怎样处理

现有材料仅支持相关性、部分帮助或推导人群时，保留限制并进入探索；实质意图错配则排除。有需要且产品能解决但缺专门文章，可以记录承接缺口。品牌身份检查独立处理，无需外部需求样本。

补查只针对能改变裁决的疑点；无新依据就停止，不为查询配额或预设题数制造证据。修订后全部重审，保留前后版本；更长、更多热点词、更容易搜到自己都不是质量提升的充分理由。
