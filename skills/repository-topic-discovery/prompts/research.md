从仓库 README 开始，沿官网/作者链接确认关联内容。建立产品能力线与已有贡献线的研究包；按需要读文档、示例、文章或研究，关键能力仍不明才针对性查实现，不全仓扫描。
本阶段是有限调查，不是穷尽研究：确认产品能力/边界、最相关的一份已有贡献（若有）、至少一个有出处的真实需求或用户场景，即可输出；其余缺口如实留待探索。最多6批网页工具调用，每批可合并独立查询/打开；优先读入口和决定性原文，不逐条追查所有潜在人群。网页返回优先 short，缺决定性依据才针对性补读，不能把未读部分算作已读。第6批后必须停止检索并输出完整研究包；不要继续追逐版本号、同类案例或非必要时间细节。预算是调查停止条件，不是允许造证据、截断关键限制或省略审核。
1. product 记录确认的能力、已有贡献和限制，以 source ID 标明依据；区分已发布、声明、计划和验证状态。contributions 写实际回答什么、能提供哪种帮助，不把文章结论当产品功能。版本易于核对则记录，否则 repository_revision=unknown。
2. 主动寻找使用触发：谁在什么事件/任务阶段或日常条件下遇到困难，现有办法为何不足，想推进什么。只保留影响适配的时间、地点、平台、成本等约束。用户给定的场景保留 user_context；推导标 inference，不强套时事。时效事实核实后才写 verified，否则条件化并记 timing_note。
3. 沿情境、症状或替代办法寻找公开原始需求，允许其否定初始人群假设。不搜自编完整长句来自证，不根据项目是否命中筛题。needs 保留原意、期待帮助类型 requested_help 与目标 outcome，text 留决定意图的短原句或准确摘要。观察到原始表达才标 observed；用户输入标 user_context；仅从能力/文章推导标 inferred，不能借作者自述冒充外部需求。
4. 同时调查需要工具/操作帮助与需要解释/评估/参考的人。已有文章可以回答宽泛问题，具体评估其贡献即可；不要把找工具的原需求改成科普需求。若未发现对应受众需求，贡献仍保留，需求标 inferred。
5. sources 给稳定 ID、完整 URL、标题、读取时间与 access；summary 保留支持判断的必要短摘录/摘要及限制，使审核者能检查原意。能力、需求与触发引用存在的 ID；用户输入无外部来源时不编 source。片段只支持实际可见的内容。
只保留决定选题的少量材料，通常覆盖 README、相关贡献和原始需求即可；不要为固定查询次数或条目数量造证据，也不要为精简截掉关键来源或限制。合理公开替代仍不可访问，或检索无新依据时，将剩余问题写 uncertainties，交付可探索的假设。
