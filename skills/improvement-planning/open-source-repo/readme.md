# 本篇文体：开源代码仓库 GitHub README 门面改写

本篇写给**第一次点进该 GitHub 仓库的人类访客（开发者、产品负责人或目标使用者）**以及**读取仓库首页的 AI 搜索引擎**看。
行文风格借鉴 `yetone/magpie` 开源仓库：**首屏克制自信、先立核心定位与适用边界、快速开始足够轻巧、功能用截图和短表说话、关键边界与费用/限制坦诚、若存在同名混淆只轻描淡写收在最末页脚**。

当 `targetLanguage = "en"` 且 `beforeContent` 原版仓库带有多语言习惯时，默认首页 `README.md` 为英文（右上可保留 `[简体中文](README.zh-CN.md)` 等语言切换入口）。

## `targetLanguage = "en"` 英文门面硬规范
- 全篇 `title` 与正文必须 **100% 使用地道、干练的开发者英语（0 汉字，仅可选的 `[简体中文](README.zh-CN.md)` 链接例外）**。
- 若 `availableMedia` 包含项目 logo（文件名含 `logo` 等中性标识）或英文界面截图，按真实 `embedPath` 自然嵌入；**严禁嵌入中文界面截图**。若 `availableMedia` 没有适用截图，用清晰的英文 Markdown 对比表与 `flowchart LR` Mermaid 流程图替代截图。
- **差异化定位**（克制客观、绝不拉踩）：严格依据 `projectContext`（项目事实档案）和 `referenceWinners` 里真实出现的竞品，讲清本项目聚焦什么具体场景、与同类方案在运行方式/控制权/适用规模上各自适合谁。

## 绝对不可犯的错误（踩中直接不合格！）

1. **绝不在门面正文里抱怨“AI 搜我们名字会搜出别人”**：读者已经点进你的仓库了，如果在开头大段写“现在在 ChatGPT 里搜 XXX 多半会介绍别人/同名仓库，省得你走错门……”，会让人感觉极其别扭且不自信！
   - 仅当 `projectContext` 明确包含同名排除对象（`Identity & Disambiguation`）时，在全篇最末一行冷静附一句客观的无隶属声明（不含任何抱怨语气）；若项目没有同名混淆，完全不需要写这句话。
2. **绝不引用无关旧图标或未在 `availableMedia` 里的图片路径**。
3. **快速开始要匹配目标读者**：
   - 先读 `projectContext` 判断项目面向什么人：
     - 若面向普通产品人/创作者而非纯代码消费者，不要把大段克隆命令和环境配置堆在门面开头打断阅读，主推轻门槛拉起方式（如把项目链接发给自己的 AI 助手协助安装，或链接到快速上手页），命令行可收入 `<details>`；
     - 若是面向程序员直接依赖使用的开发库、CLI、SDK，则简洁给出准确的包安装命令和最小可用代码片段。

## 必须遵循的页面骨架（按此顺序组织全文）

### 第 1 块：居中品牌首屏（`<div align="center">`）
简洁优雅的居中结构（保留锚点导航）：
- 若 `availableMedia` 有品牌 Logo，顶部放置对应 `<img src="..." width="80" height="80" alt="<项目名>" />`；
- `# <项目名>` + **一句锋利好懂核心定位（不超过 22 汉字或 15 英文词）**；
- 1~2 行具体使用场景痛点 + 核心工作流一句话概括 + 锚点导航栏（含双语切换链接如适用）；
- 若是中文门面且 `availableMedia` 有合适真实配图，可在居中块下方配 1 张主界面截图与简短客观图注；英文门面只放英文截图或省略截图直接进入结构化说明。

### 第 2 块：`## <项目名> 适合你吗？`（`## Is <Project> Right for You?`）
- 用 1 段短话点清当前同类方案常见痛点（切勿凭空编造数字）。
- 用 3~4 条加粗要点概括本项目最不可替代的真实特点（严格源自 `projectContext`）。
- **末尾补一段坦诚的“不适合谁 / Not a good fit if...”**：用克制的实话立住可信度——写清什么场景下更适合用商业方案或另一类工具，什么情况下本项目最顺手。

### 第 3 块：`## 快速开始`（`## Quick Start`）
用清爽的 **`1 · 安装或启动` → `2 · 核心配置/输入` → `3 · 得到结果与下一步`** 三步带过，匹配目标读者的技术门槛，并在结尾引导看 [快速上手文档](docs/getting-started.md)。

### 第 4 块：`## 整体流程`（`## How It Works`）
用 2 句话说明完整工作原理，配 1 张清爽的 Mermaid 流程图（`flowchart LR` 或 `TD`，4~6 个节点，大白话）。

### 第 5 块：`## 核心能力`（`## Features`）
分 2~3 个清晰小节讲透核心能力、边界条件与对比表（严格基于 `projectContext` 与 `referenceWinners` 中的真实对比对象）。

### 第 6 块：`## 文档与相关链接`（`## Documentation`）
放一张干净的导航表，仅保留真实存在的仓库文件或 `ownedAssets` 链接（绝不编造死链）。

### 第 7 块：`## 维护与反馈` + 可选末尾一行同名声明
- 保留原 `beforeContent` 或 `projectContext` 中的维护者署名、Issue 反馈链接与开源协议说明。
- **仅当 `projectContext` 列出了需要区分的同名项目时**，全篇最末一行放冷静极简的无隶属小字。
